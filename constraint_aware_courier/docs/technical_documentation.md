# Technical Documentation

## 1. Data Model

### Orders (`data/raw/orders.csv`)
| Field | Type | Description |
|---|---|---|
| order_id | str | Unique order identifier |
| customer_id | str | Synthetic customer identifier |
| location_id / building_name / location_type | str | Delivery building (gated apartment or office complex) |
| latitude / longitude | float | Delivery coordinates (synthetic, clustered around ~40 buildings) |
| product_type / product_category | str | SKU-level type and one of 6 broad categories (Normal, Fragile, Heavy, Frozen, Hot Food, Chemical) |
| weight_kg / volume_litre | float | Package weight and volume, category-dependent distributions |
| fragile | bool | Fragile handling flag |
| temperature_requirement | str | Ambient / Frozen / Hot |
| incompatible_group | str or null | Fine-grained conflict group (e.g. two different cold-chain vendors) |
| pickup_ready_time | datetime | When the order becomes physically ready for pickup |
| order_created_time | datetime | When the customer order was placed |
| promised_start_time / promised_deadline | datetime | The delivery service window |
| priority | str | URGENT / HIGH / NORMAL / LOW |
| service_time_minutes | float | Time to hand over the package at the door |
| status | str | Order lifecycle status |

### Riders (`data/raw/riders.csv`)
| Field | Type | Description |
|---|---|---|
| rider_id | str | Unique rider identifier |
| capacity_kg / capacity_volume | float | Maximum payload per single batch/trip |
| shift_start / shift_end | datetime | Working hours |
| current_latitude / current_longitude | float | Rider's starting position for the day |
| max_orders_per_batch | int | Cap on number of orders in one trip |
| max_workload_minutes | int | Operational cap on workload per shift |
| availability | str | AVAILABLE / UNAVAILABLE (used by disruption scenarios) |

Both datasets are generated by `src/data_generator.py` with a fixed random
seed (`config.RANDOM_SEED = 42`) for full reproducibility.

## 2. Baseline Algorithm (`src/baseline.py`)

A simple nearest-neighbour, capacity-aware batching strategy:
1. Orders are sorted by distance from the pickup hub.
2. Orders are round-robin assigned to the nearest rider with weight/volume/
   order-count headroom.
3. **No compatibility, deadline, readiness, or workload checks gate
   assignment** -- these are only *measured* afterwards and reported as
   violations, to provide a fair "naive system" comparison point.
4. Riders repeat pickup rounds until their shift ends or no orders remain
   (multi-batch-per-shift simulation), so the whole operating day is
   modelled, not a single snapshot.

## 3. Constraint-Aware Batching Algorithm (CABA) (`src/batching_algorithm.py`)

CABA is a **constructive greedy heuristic with explicit constraint checking**
and a multi-objective scoring function. Exact combinatorial optimisation
across 1000+ orders and 50+ riders under 8 simultaneous constraints is
computationally infeasible for a real-time system, so CABA instead:

1. Processes orders in priority order: URGENT first, then earliest
   pickup-ready time (Constraint 7).
2. For each order, evaluates every currently open batch (one per active
   rider in the current pickup round) against the hard constraints, in this
   order (fail-fast, cheapest checks first):
   - Capacity (weight, volume, order count)
   - Product compatibility (category matrix + fine-grained group conflicts)
   - Maximum stops per batch
   - Pickup readiness (bounded rider waiting time)
   - Deadline feasibility (including a safety buffer)
   - Rider workload (rejects if workload would reach the EXCESSIVE band)
3. Among all *feasible* insertion points, the one with the lowest resulting
   Batch Score (Section 4 below) is chosen.
4. If no open batch can take the order, a new batch is opened with the
   nearest unused, available rider (if the order can feasibly start there).
5. If no rider anywhere can feasibly take the order in the current round,
   it is deferred to the next round; if it still cannot be placed once no
   rider has shift time remaining, it is reported as **unassigned** with an
   explicit reason -- never silently dropped.
6. Riders complete multiple such rounds across their shift, mirroring a
   real operating day.

## 4. Objective Function (Batch Score)

```
Batch Score = distance_cost
            + deadline_risk_penalty
            + workload_penalty
            + waiting_time_penalty
            - urgent_priority_bonus (if the batch contains an urgent order)
```

Weights (see `config.py`):
- `WEIGHT_DISTANCE = 1.0`
- `WEIGHT_DEADLINE_RISK = 4.0` (heavily penalises batches that cut it close
  to the promised deadline, even if technically still feasible)
- `WEIGHT_WORKLOAD = 2.0`
- `WEIGHT_WAITING_TIME = 1.5`
- `URGENT_PRIORITY_BONUS = 25.0` (score reduction that biases urgent orders
  toward the best available batch)

**Hard constraints are never scored** -- an infeasible batch (e.g. one that
mixes Frozen and Hot Food, or exceeds capacity) is rejected outright before
the objective function is even evaluated. This guarantees the priority
order stated in the spec: (1) no product violations, (2) no capacity
violations, (3) no promised-time violations, (4) reasonable workload,
(5) reduced distance.

## 5. Routing Layer (`src/routing.py`)

Routing is implemented as a **pluggable layer**, not a single hard-coded
distance function:

```
Coordinates
    |
    v
Routing LAYER
    |-- HaversineRoutingProvider   (current / default -- implemented, always available)
    '-- OSRMRoutingProvider        (future / optional -- documented stub, NOT implemented)
    |
    v
Travel distance + estimated travel time
    |
    v
Constraint-aware batching
```

- `RoutingProvider` is an abstract base class with two methods:
  `distance_km()` and `travel_time_minutes()`.
- `HaversineRoutingProvider` (the active default, `config.ROUTING_PROVIDER =
  "haversine"`) implements these using Haversine great-circle distance and
  a configurable average speed (`AVERAGE_SPEED_KMPH`), scaled by a
  `delay_multiplier` for disruption scenarios (e.g. 1.75x for Scenario B).
- `OSRMRoutingProvider` is a **documented interface stub** for a future
  real-road-routing integration (e.g. a self-hosted OSRM or
  OpenRouteService instance). It is wired into the exact same interface as
  Haversine but deliberately raises `NotImplementedError` with instructions
  for what a future implementer would need to do -- selecting it does not
  silently fall back to Haversine, so it can never produce misleading
  results.
- `get_routing_provider(name)` is the factory function; `baseline.py` and
  `batching_algorithm.py` never compute distance/time themselves -- they
  only call `routing.estimate_batch_route()`, `routing.haversine_distance_km()`,
  and `routing.travel_time_minutes()`, which delegate to whichever provider
  is configured. **Swapping in real road routing later is therefore a
  one-file change.**
- Building access delay: fixed minutes per distinct stop
  (`BUILDING_ACCESS_DELAY_MIN`), modelling security/lift/reception time.
- Delivery sequencing: nearest-neighbour heuristic from the pickup hub
  through all stops in a batch (not full TSP -- see `docs/limitations.md`),
  implemented once on top of the provider interface so every provider gets
  it for free.

**Every result in this project's reports and dashboard was generated with
the Haversine provider** -- there is no live maps or traffic API call
involved, by design (per spec Section 9). This is disclosed clearly as a
current limitation / future enhancement, not hidden behind the abstraction.

## 5b. Recovery / Re-evaluation Queue (`src/batching_algorithm.py -> _recovery_pass`)

```
Orders
  |
  v
Initial multi-round batching
  |
  +-- Valid ---------------------------> Batch
  +-- Invalid
        |
        v
  Re-evaluation queue
        |
        v
  Try alternative rider (full fleet, not just this round's riders)
        |
        v
  Try secondary dispatch window (a dedicated extra trip, starting the
  moment ANY rider's shift allows -- not waiting for their next round)
        |
        v
  Re-check workload -> re-check deadline (same hard-constraint gate used
  everywhere else; no shortcuts, no forced assignment)
        |
        +-- Feasible -----> Reassign (dedicated recovery batch)
        +-- Not feasible -> Remain unassigned (reason logged)
```

After the main multi-round loop finishes, every order that is still
unassigned gets one more explicit, fully logged attempt against the
**entire current rider pool** -- including riders it was never compared
against during its original round, due to the greedy single-pass insertion
order. This directly tests whether an unassigned order failed because of
genuine infeasibility or because of insertion-order luck.

Each attempt is recorded in `recovery_log` as a trace:
`{order_id, attempts: [{rider_id, reason}, ...], final_result, final_reason}`.
This is what drives the "Why was this order rejected?" dashboard table and
`reports/failure_analysis.csv`'s `recovery_attempted` /
`riders_tried_in_recovery` columns.

**Critically, recovery never relaxes a constraint to force an assignment**
-- a recovered order still has to pass the exact same `_try_insert()` gate
(capacity, compatibility, max stops, readiness, deadline, workload) as any
normal batch insertion. On the bundled dataset, the recovery pass recovers
**0 of 182** Normal Day unassigned orders (and 0 of 327 / 0 of 183 in the
two most severe disruption scenarios) -- every single one was tried against
all 55 riders and failed for the same reason (deadline infeasibility),
which rules out insertion-order luck as the explanation and confirms these
orders are genuinely infeasible given the fleet's capacity and timing (see
`docs/error_analysis.md` Section 5b for the full investigation, including
the finding that 100% of unassigned orders are NORMAL/LOW priority).

## 6. Workload Calculation (`src/workload.py`)

```
workload_score = service_time + access_time + waiting_time + handling_time
```

- `service_time`: sum of each order's `service_time_minutes`.
- `access_time`: `distinct_stops * BUILDING_ACCESS_DELAY_MIN`.
- `waiting_time`: total minutes the rider must wait for not-yet-ready orders.
- `handling_time`: base handling overhead per package, with extra minutes
  for fragile, heavy, and frozen items (careful handling / insulated bags).

The resulting total is classified into LOW / MEDIUM / HIGH / EXCESSIVE
bands (`config.WORKLOAD_BANDS`), and any batch at or above
`WORKLOAD_REJECTION_THRESHOLD_MIN` (210 minutes) is rejected by CABA.

## 7. Disruption Handling (`src/disruption.py`)

| Scenario | Mechanism |
|---|---|
| A. Rider capacity loss | A random fraction (default 25%) of riders are marked `UNAVAILABLE`; both algorithms are re-run against the reduced fleet. |
| B. Travel delay | A `delay_multiplier` (default 1.75x) is applied throughout routing/time estimation, without altering the underlying distance model. |
| C. Urgent demand surge | A fraction (default 15%) of non-urgent orders are converted to `URGENT` with a tightened `promised_deadline`. |

Both the baseline and CABA are run on **exactly the same disrupted input
data** in each scenario, ensuring a fair comparison.

## 8. Evaluation Methodology (`src/evaluation.py`)

For each algorithm run, the following are measured directly from the batch
output (never fabricated):
- Total distance, average distance/order
- Number of batches, average batch size
- Deadline / product / capacity / readiness / workload violation counts
- Average and maximum rider workload
- On-time delivery rate (overall and urgent-only)
- Unassigned order count
- Wall-clock execution time

`compare_algorithms()` runs both algorithms on the identical input dataset
and produces the side-by-side comparison table (`Metric, Baseline, CABA,
Improvement %`) used throughout the app and reports.
