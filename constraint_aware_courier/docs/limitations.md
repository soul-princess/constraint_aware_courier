# Limitations

This project is an academic prototype. The following limitations are
deliberate, documented simplifications -- not oversights -- and should be
disclosed in any presentation of the results.

## Data
- **Synthetic data.** No real company, customer, or courier data was
  available or used. All orders, riders, buildings, and product
  distributions in `data/raw/` are generated by `src/data_generator.py`
  using `numpy` with a fixed seed. Distributions were chosen to be
  *plausible* (e.g. category-dependent weight/volume ranges, a minority of
  urgent/tight-window/not-ready orders) but are not calibrated against any
  real operational dataset.
- **Single pickup hub.** All orders are modelled as originating from one
  central hub. Real operations often use multiple micro-fulfilment centres
  or restaurant/seller pickup points; `pickup_ready_time` partially
  compensates for this by modelling per-order readiness independently, but
  the routing model still assumes one physical pickup location.

## Routing
- **No real-time GPS or live traffic API.** Travel time is estimated as
  `distance / average_speed`, with a configurable multiplier for disruption
  scenarios. It does not reflect actual road networks, one-way streets,
  traffic signals, or real-time congestion. Routing is implemented as a
  pluggable layer (`src/routing.py`) specifically so this can change without
  touching the batching algorithms: a documented `OSRMRoutingProvider` stub
  exists for a future self-hosted OSRM/OpenRouteService integration, but it
  is intentionally *not implemented* in this prototype -- selecting it
  raises `NotImplementedError` rather than silently approximating real
  routing. Every number in this project's reports was generated with the
  Haversine provider.
- **Haversine distance, not road distance.** Straight-line distance
  underestimates actual road travel distance, typically by a factor that
  varies by urban layout (commonly cited real-world circuity factors are
  roughly 1.2-1.4x for dense urban grids). This project does not apply a
  circuity correction factor, which means absolute distance/time figures
  should be read as directional (relative comparisons between baseline and
  CABA are still fair, since both use the identical model).
- **Nearest-neighbour route sequencing, not solved TSP.** Delivery stop
  order within a batch uses a nearest-neighbour heuristic, which is fast and
  explainable but not guaranteed optimal for batches with several stops.

## Building Access Model
- **Fixed access delay per stop.** A flat `BUILDING_ACCESS_DELAY_MIN`
  applies to every stop, when in reality gated apartments and office
  complexes vary widely in security/lift wait times, and even repeat visits
  to the same building on the same day might have different delays (e.g.
  first visit requires security registration, later visits do not).

## Product Compatibility
- **Simplified compatibility matrix.** The 6-category compatibility matrix
  (`src/constraints.py`) is a reasonable, explainable model of real
  logistics conflicts (temperature, crush risk, chemical safety) but does
  not capture every real-world SKU-level nuance. The `incompatible_group`
  field adds one layer of fine-grained conflict modelling but is itself a
  simplification of what a real product-safety team would maintain.

## Algorithm
- **Greedy heuristic, not exact optimum.** CABA does not guarantee the
  mathematically optimal batch assignment (see `docs/methodology.md` for
  why this is an appropriate trade-off for a real-time academic
  prototype). A different (slower) metaheuristic could plausibly find a
  better solution on the same data.
- **Insertion order matters.** Orders are processed urgent-first,
  then earliest-ready-first. This is one reasonable priority policy;
  changing it would change which specific orders end up unassigned when
  capacity is genuinely insufficient.

## User Validation
- **Simulated, not real, stakeholder feedback.** `reports/user_feedback.csv`
  contains a validation questionnaire template and clearly-labelled
  SIMULATED example responses for demonstration purposes only. No real
  riders, operations staff, or managers were surveyed for this academic
  project.

## Honest Trade-off Disclosed by the Experiments
Across all four experiment scenarios (see `reports/experiment_results.csv`),
CABA consistently achieves **zero constraint violations** and **100%
on-time delivery** for the orders it assigns, at the cost of leaving a
meaningful fraction of orders unassigned (typically 18-33%) when the
combination of tight deadlines and fleet capacity makes on-time,
constraint-respecting delivery genuinely infeasible for those specific
orders. The baseline serves every order but with substantial deadline,
compatibility, readiness, and workload violations. This is a real,
measured trade-off between **service completeness** and **service
reliability** -- see `reports/failure_analysis.csv` for the itemized
reasons behind every unassigned order, and the Error Analysis section of
the presentation for discussion.
